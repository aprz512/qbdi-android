# 中文 README 与代码质量审查设计

## 目标

面向希望直接复现实验的 Android 逆向与安全工程师，用中文重写项目 README，使读者能理解项目用途、核心能力、运行条件、完整操作流程和真实性能边界。同时对当前仓库做一次代码质量审查，在交付说明中按严重程度报告可复现、可定位的问题。

## README 结构

README 采用任务流组织：

1. 项目介绍与适用范围。
2. 核心特性与采集链路。
3. 环境要求和已知限制。
4. 构建、安装、部署、场景偏移配置、Frida 注入、轨迹拉取与转换。
5. `fast`、`balanced`、`full` 三种采集配置的差异。
6. Pixel 6 实测性能、测试条件和指标口径。
7. Flight Recorder、崩溃恢复、故障排查及深入文档入口。

命令以仓库现有脚本和 Gradle 任务为准。复杂协议细节链接到 `docs/`，README 只保留完成首次实验所需的信息。

## 性能口径

性能数据引用 `docs/benchmarks/binary-trace-baseline.md` 中同一设备、同一工作负载、一次预热后五个独立进程的中位数。正文必须同时写明 Pixel 6、Android 16、arm64-v8a、Debug、21,718 条指令和 256 次迭代。

`elapsed_ms` 只统计被追踪目标执行和生产者回调的热路径，不包括最终写入器排空、尾记录与指标文件发布、ADB 拉取和主机转换。README 不把这些数据表述成所有设备上的性能保证。

## 代码质量审查

审查当前 `HEAD` 的一方代码，排除 vendored 的 QBDI、ShadowHook 和 LZ4 实现。重点检查：

- 构建配置与可复现性；
- C++ 生命周期、资源管理、并发和错误传播；
- Python/JavaScript 工具的输入校验、失败语义和可测试性；
- Kotlin/JNI 边界；
- 自动化测试覆盖与文档一致性。

每项发现必须包含严重程度、文件与行号、实际风险和建议修复方向。没有证据的问题不列入结果；由格式化器或测试自动保证的风格问题不重复报告。

## 修改边界

本次只修改 README 及本设计/后续计划文档，不修改功能代码。代码质量问题作为审查结论交付，后续是否修复由用户另行决定。
