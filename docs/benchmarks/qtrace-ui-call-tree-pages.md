# 调用树分页与页面缓存诊断

## UI-02：服务端分页（2026-09-24）

日期：2026-09-24。此结果来自当前开发机的本地诊断，不是固定性能参考主机门禁。

## 语料与方法

- 两个 QTRB 1.2 单文件语料，各 10,000 条 instruction、340,345 字节、5,000 个调用帧。
- 宽树交替写入 call/return，形成 5,000 个根帧；深树先写入 5,000 个 call，再写入 5,000 个 return，形成 5,000 层嵌套。
- 使用仓库 `scripts.tests.test_trace_binary` 和 `scripts.tests.test_flight_trace` 的 QTRB 编码辅助函数；call 的定义标志为 `5`，return 为 `9`。两份语料只保存在 `/tmp/qtrace-call-tree-corpus/`，不进入仓库。
- Release 构建在同一机器运行五轮。每轮打开 artifact，首次请求调用树；宽树依次读取 50 个根节点页，深树依次展开 5,000 层。逐页校验树身份，累计节点数恰为 5,000；记录首次构建耗时、服务端分页 p95 和序列化 JSON 最大字节数。

| 语料 | 五轮首次构建 ms | 中位数 ms | 五轮分页 p95 ms | 最大单页 JSON |
| --- | --- | ---: | --- | ---: |
| 宽树 | 51.095、51.636、51.970、52.271、51.150 | 51.636 | 0.012、0.012、0.013、0.011、0.015 | 18,881 B |
| 深树 | 60.692、60.014、57.139、57.757、57.881 | 57.881 | 均小于 0.001 | 357 B |

前端自动化测试以 100 个已加载根节点、10,000 个声明总节点验证：DOM 中调用帧始终少于 20 个；滚动到底部后按需请求下一页。Rust 测试检查身份、非法父节点、树切换和工作区关闭。此测量只证明新分页路径的上界与正确遍历；没有旧版相同语料的耗时对照。

## UI-10：页面缓存（2026-10-19）

基于 `5c269e0` 的当前工作区。此前折叠仅隐藏子节点，已加载页面仍留在 Map；根节点翻页也会不断拼接数组。DOM 虚拟化没有限制这些累计数据。

### 保留策略与边界

- 每个父节点只保留一页、每页至多 100 个节点；使用 `Load more calls` 和 `Previous calls` 双向翻页。切换页面时清除已离开窗口的后代页面及展开状态。
- 页面缓存同时限制为 8,192 个节点与 4 MiB 计量权重。权重按字符串长度和对象预留空间计算，不序列化整页，也不声称浏览器实际 heap 小于 4 MiB。
- 缓存按最近访问顺序淘汰分支，同时保护当前请求的祖先路径。被淘汰的分支可在重新展开或点击 `Load calls` 后重取；不会保留无可达父节点的页面。
- 请求按父节点合并，最多同时保留四个请求。响应核对树身份、artifact、timeline、线程、父节点和 offset；关闭或换树后不接收旧响应。父节点已离开窗口时，不恢复其迟到的子页面。
- 翻页保留可见节点锚点；根页切换回到页首。节点保留实际兄弟位置和总数的 ARIA 属性，事件跳转仍使用原始 source row。
- 祖先路径自身超过预算时保留当前视图并提示限制，不通过淘汰祖先继续提交不可达页面。已有 5,000 层、每层一个节点的导航结构可完整保留；更宽且持续展开的路径仍受预算约束。

### 五轮本机对比

同一机器、Chromium 153.0.8010.12、相同依赖和合成负载，优化前后各五轮。每轮使用独立浏览器页面，挂载实际 `CallTreePane`，依次展开、折叠 100 个根分支，每个分支加载 100 个子节点；display 含 256 字符填充。挂载后和浏览结束后各强制 GC，再读取 `Runtime.getHeapUsage`。该结果是整个诊断页面的 heap 增量，包含 React 开销，不等于缓存权重。

| 指标（五轮中位数） | 优化前 | 优化后 |
| --- | ---: | ---: |
| 浏览后的 heap 增量 | 4,272,520 B（4.07 MiB） | 3,407,176 B（3.25 MiB） |
| 展开至两次 animation frame 的 p95 | 33.6 ms | 33.5 ms |
| frame interval p95 | 16.8 ms | 16.7 ms |

Heap 增量减少 **20.25%**。前后各轮 DOM 最大均为 18 个调用节点，全部完成 100 次加载和预期 source row 跳转。帧时间基本不变；包含两次 animation frame 的展开耗时不能证明 JavaScript 执行加速。

复现命令：

```bash
node qtrace-ui/tools/call_tree_memory.mjs /tmp/qtrace-call-tree-memory.json
```

五轮原始样本、源码哈希与验收记录见 [页面内存证据](qtrace-call-tree-memory-2026-10-19.json)。旧版使用 `5c269e0` 的组件源码；诊断脚本新增的主机与依赖字段仅影响报告元数据，不改变测量负载。

### 正确性与验收范围

新增 11 项测试覆盖节点与权重上限、LRU、祖先保护、过大页面拒绝、不可达后代回收、5,000 层路径、淘汰重取、双向翻页与滚动、请求合并、迟到响应和失败重试。两项交互回归在隔离目录使用原组件时均失败，当前实现均通过。

四份保留的小米产物再次通过 Chromium 与真实 Rust 服务的功能验收，包括 1,185,909 个事件的 Flight：展开、折叠、缓存重开和子节点事件跳转，以及上下文、筛选、寄存器、内存及历史、标注和服务重启持久化。四份产物的首次根页都不超过 100 个节点；真实产物的根页双向翻页未触发，其覆盖来自组件回归。没有重新进行 Android 采集。

本机 Chromium heap 诊断不替代固定主机规模门禁、Tauri WebKit 测量、高缩放布局或设备性能验收。Rust 服务和协议未修改，先前服务端分页数据保持原样。
