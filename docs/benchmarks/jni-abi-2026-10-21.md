## 根因与修复

旧采集只复制 GPR，并把 x8 当作第八个去除 env 后的参数。
旧 formatter 将普通/V/A 调用全部按连续 GPR 展开，导致 V 的 `va_list` 地址和 A 的 `jvalue*` 地址被显示成首个 Java int。
它还忽略 GP/FP 寄存器组、栈参数、C 默认参数提升和 JNI 整数符号；浮点返回错误读取 x0。

真实设备的旧版本中，首个 V 调用 Java 收到 `2`，文本却显示 `488908045248`。
普通调用中的 `-38` 显示成 `4294967258`；混合调用的 double/float 文本也来自错误寄存器。
同一轮 Java 实收值、native 返回、异常、x18 和真实栈检查全部正确，因此故障定位于观测解码层。
修复增加独立的 AAPCS64 解码器，并将 FP 状态传入 JNI enter/leave；无法确定时明确输出未解码原因。

另一个 Host 回归证明单个 TLS 快照会在嵌套 JNI 后丢失外层 leave。
现由各 pending transfer 持有快照，未识别的 native 转移也平衡自己的 return，不再消费外层 JNI 返回。
补充回归还覆盖已耗尽保存区的正 `va_list` 偏移；该合法形式按 AAPCS64 继续读取栈参数。
